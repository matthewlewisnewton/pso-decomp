# Reviewed per-unit compiler configuration admission

This source proposal adds a recovery-only path for one explicitly reviewed `GAME_EXCEPTIONS` entry per packet. It supports only absent → inherited GC/2.6 with deferred inlining, absent → GC/2.0 with deferred inlining, and GC/2.6 → GC/2.0 with the same deferred-inlining expression. A separate closed player profile permits only absent → GC/1.3.2 with inherited default flags for `pso/player/TObjPlayer_802D5B78.cpp`; its caller `pso/player/TObjPlayer_802D5174.cpp` must retain GC/2.6 and its default flags. The exact compiler SHA-256 identities are fixed in the checker; GC/1.3.2r and a caller override are rejected. Mixed-unit changes require a separate extension. The static checker does not execute configuration; it compares raw bytes outside the entry and reviewed contiguous comments and rejects computed or duplicate keys, other expressions, control framing, unsupported profiles and no-ops. Changed `tools/` remain forbidden. Source-maintenance and tools-only maintenance do not gain a configuration exception, and recovery still requires positive gain.

This is not an installation or pilot authorization. Deploy only independently reviewed, pinned copies of the CLI, checker, preparation launcher, acceptance adapter and guard outside every writable candidate root. The legacy validator remains unchanged and rejects configuration changes. Do not alter a live queue pin or reuse a frozen batch for this proposal.

## Operator-selected review packet

The recovery manifest's optional `config_admission` contains exactly `checker` and `packet`, each an absolute external `path` and `sha256`. It is mandatory when, and only when, the selected recovery changes `configure.py`. The queue plans a deterministic candidate and invokes the pinned checker under isolated Python; a missing, stale, malformed or gratuitous packet rejects. The operator selects the packet through the existing trusted review channel: a reviewer name and a Boolean alone are not authentication.

The packet is strict JSON with no duplicate or unknown fields. It contains:

- `version: 1`, `repository`, `policy: "recovery"`, `verdict: "pass"`, `independent: true` and `reviewer`.
- The exact `target`, planned `candidate` and `tree`, plus ordered `prs` with `number`, `head`, `base_sha`, `review_base` and pinned `review` evidence (`path`, `sha256`). The planned merge commits and their exact parents are checked against this order.
- `steps`, one entry for every incremental configuration change, and `cumulative`, the target-to-candidate entry. Each has `before`, `after`, `before_blob`, `after_blob`, `diff_sha256`, `unit`, `old_profile`, `new_profile`, `before_sha256`, `after_sha256`, `before_span_sha256` and `after_span_sha256`. The diff is Git's full-index, binary, no-external-diff, no-textconv, no-renames output with fixed diff settings. Complete source trees are bound by commit/tree identities; comments and the full blobs are hashed, not merely AST-equivalent.
- `pins`: pinned external files named `checker`, `cli`, `python`, `launcher`, `wrapper`, `adapter`, `guard`, `base_validator`, `compiler`, `compiler_wrapper`, `git`, `preparer` and `ninja`. Each entry is `{ "path": ..., "sha256": ... }`. The compiler executable must be inside the pinned compiler directory and the compiler wrapper must equal the configure wrapper; names alone never establish identity.
- `configure_paths`: pinned `dtk`, `objdiff`, `wrapper`, `compilers` and `binutils` paths. Tool directories use a SHA-256 of compact JSON for sorted `[relative_path, "file", mode, file_sha256]` and `[relative_path, "directory", mode]` records; symlinks and empty directories reject. Files use their raw SHA-256.
- `originals` for `baseline` and `candidate`, each with `dol_sha256` and `tree_sha256`. The tree hash uses the same sorted inventory algorithm. Both actual DOLs must also match the fixed original SHA-1.
- `ordered_inputs` for each root, with `ordered_inputs_sha256`, `source_inputs` and `fallback_inputs`, and `effective_argv`, the complete reviewed ordered compile argv beginning with the pinned compiler wrapper and compiler. `dependent_compile` is empty for Ancient01; for the player profile it contains exactly the caller unit, pinned GC/2.6 compiler and its complete reviewed argv. A separately reviewed recovery may declare different baseline and candidate link inputs; the actual results must match both declarations. The packet never authorizes loss of previously preserved ranges.

## Preparation boundary

Use fresh, exclusively reserved baseline and candidate roots and an already reviewed isolated Python launcher that enforces `-I -B`; it must be pinned in the packet. Prepare immutable original copies using the existing exclusive protocol, release that lock, then invoke the independently installed preparation launcher separately for each role. The request JSON contains `packet`, absolute `repo`, `role`, `target`, `candidate`, `tree`, `prs`, the ordered planned `commits`, absolute fresh `receipt`, pinned `plan_receipt` (`path` and `sha256`), `original_sha256` and `original_tree_sha256`. Invoke:

```text
python -I /reviewed/merge_batch_config_prepare.py --request /private/request.json --checker /reviewed/merge_batch_config_delta.py --checker-sha256 REVIEWED_SHA256
```

The launcher runs the full static and identity preflight before waiting and repeats it after acquiring the existing legacy exclusive lock, immediately before calling the pinned isolated launcher for `configure.py`. It rejects reused generated state, dirty tracked inputs, ignored Python import files, changed tool/import closure, original inputs and stale packet evidence. It rechecks identities after configuration and exclusively writes a receipt containing the packet, root, source/tree, graph, tool and effective-argv hashes. Interrupted or stale roots are preserved for investigation; use a fresh root and review rather than editing receipts.

After releasing the launcher lock, the existing wrapper owns its own preparation and scheduling locks. An independent reviewer must inspect the actual graph and all relevant compile edges, confirm the declared effective argv and compiler identity, prove unlisted edges unchanged, and bind the exact graph and both config-preflight receipts into the graph review. Each root entry includes pinned `config_preflight` and `original_tree_sha256`; the review includes `config_packet_sha256`, `config_plan_sha256`, `effective_compile_argv`, `ordered_input_provenance`, and `dependent_compile` matching the packet, plus true attestations `configuration_edge_review`, `unlisted_edges_unchanged`, `compiler_binding_reviewed` and `no_setup_execution`. The player case additionally requires `caller_gc26_reviewed: true`. Actual reviewed graph proof is a separate boundary, not inferred from packet hashes. No setup or download command may run from the frozen acceptance graph.

The acceptance adapter queries the pinned Ninja compilation database without running a build and compares the target command to the reviewed argv; for the player case it also compares the caller command in both graphs. It revalidates the packet, CLI/guard/adapter/wrapper identities, source trees, roots, original inputs, preparation receipts and graph review at every admission. It compares observed actual linker provenance with the reviewed before/after values, then applies the existing DOL, full source checks and unfiltered raw coverage/exact/source-link and padding-loss gates. Before the single exact-old CAS push, the queue rechecks the pinned request and calls the external adapter's configuration contract again. Any stale evidence rejects; no lost range or padding is waived. Actual source review, current main, frozen heads, fresh graph review and a separately coordinated pilot remain mandatory.
